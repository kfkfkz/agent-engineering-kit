# 项目记忆（坑与流程经验）

沉淀项目开发中的两类经验，供开发者与所有协作 AI Agent（Claude Code、Codex 等）共用。
入口指引已分别写入 `CLAUDE.md` 与 `AGENTS.md`。

| 目录 | 内容 | 粒度 |
| --- | --- | --- |
| `pitfalls/` | 代码坑：缺陷根因、误用陷阱、链路陷阱 | 一条一文件 |
| `playbooks/` | 流程手册：环境操作、测试数据、检查清单 | 一个主题一文件 |

## 使用规则（对 Agent 同样生效）

1. 动手修改代码前，先查下方索引，命中相关条目必须先读全文。
2. 状态为「待验证」的条目仅供了解，不得作为修改依据。
3. Bug 修复经人工审核通过后，将原因、影响范围、修复方案整理为新条目入库（素材即审核通过的 bug 分析，零额外成本）。
4. 条目过时后将其状态改为 `deprecated`，不删除，保留可追溯性。
5. 遵循安全要求：条目中禁止出现密钥、Token、真实 PII、内网地址。
6. **功能验收通过后进行功能蒸馏**：按下方「功能蒸馏」清单将核心流程与环境信息沉淀为 playbook 条目。

## 功能蒸馏清单

功能验收通过后，对该功能蒸馏以下内容入库：

| 蒸馏项 | 去处 | 内容 |
| --- | --- | --- |
| 核心流程 | `playbooks/` | 端到端可执行步骤（谁调用谁、接口顺序）、涉及的组件/算法包清单 |
| 环境信息 | `playbooks/` | 部署环境、服务路由前缀、关键配置项（凭证除外，写获取途径） |
| 可复用测试数据 | `playbooks/` | 现成的场景/资源 ID，附「最后有效」日期 |
| 过程中踩的坑 | `pitfalls/` | 功能开发/测试期间定位的缺陷与陷阱 |
| 权威文档指针 | playbook 内 | spec/接口文档等详细文档的位置，报文细节不复制 |

原则：记忆区存"怎么跑通"和"去哪查详情"，不复制权威文档内容（单一口径）。

## 条目大小与时效（压缩与矫正）

记忆条目会随时间膨胀和失实（接口改了、ID 换了、路径移了），必须定期压缩与矫正，否则会误导后续 Agent。**过期的记忆比没有记忆更危险。**

### 大小约束

- pitfall 条目 ≤ 60 行，playbook ≤ 150 行；超出时压缩：过程细节（报文、步骤明细）下沉到权威文档并保留指针，或按主题拆分条目。
- 压缩不删「状态/触发/根因结论」，只下沉过程细节。
- README 索引表一句话 ≤ 40 字。

### 时效规则

- 每个条目必须带日期：pitfall 为定位日期，playbook 为「最后有效」日期。
- **用后即校**：任何 Agent 或人引用条目时发现与现状不符，必须当场矫正内容并更新日期；无法确认的标记 `deprecated`。
- **定期巡检**：每个迭代周期或大功能开工前，执行一次巡检（Claude Code 用 `/memory-check`，其他 Agent 按"巡检步骤"执行）。

### 巡检步骤（Agent 可执行）

1. 逐条读取条目，无「校验点」小节的从正文提取可核验事实（接口路由、类/方法名、文件路径、配置键）生成该小节。
2. 对每个校验点比对当前代码库：代码查询优先用代码知识图谱/结构化检索工具（如可用），grep 兜底（注意：服务路由前缀通常在 application 配置的 context-path，直接搜路径字面量可能搜不到）。核验路由是否仍存在、类/方法逻辑是否未变、文件是否还在。
3. 失配条目：修正正文与校验点，更新日期；无法确认的列出待人工决定是否 `deprecated`。
4. 超限条目按「大小约束」压缩，并同步 README 索引。
5. 输出报告：本次矫正/压缩了什么、哪些存疑；巡检只改 `docs/memory/` 内文档，不改代码；`deprecated` 需人工确认。

## 新条目模板（pitfalls）

文件命名：`YYYY-MM-DD-<slug>.md`，日期为问题定位日期。

```markdown
# <一句话标题>

- 状态: 已确认 / 待验证 / deprecated
- 模块: <涉及模块/服务>
- 触发: <改动哪类代码、配置，或排查哪类问题时需要读本条>

## 现象

## 根因

## 修复方案

## 验证

## 校验点
（列出可机器核验的事实：接口路由、类/方法名、文件路径、配置键，供巡检比对）
```

playbooks 无固定模板，但须写明适用环境与「最后有效」日期。
