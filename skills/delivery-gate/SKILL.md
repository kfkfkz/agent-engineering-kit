# 交付门禁
## 治理等级（governance profile）

**第一步：读取 `.repo-memory-kit/governance`**——它决定本节的回执形态要求。

- **strict**（默认）：所有非平凡变更必须落正式验证回执（`docs/delivery-receipts/`）
- **lightweight**（`install.sh --lightweight` 启用）：仅**高风险变更**（数据库
  schema、外部 API 契约、安全域）要求独立回执文件；低风险变更（文案/配置/
  纯内部重构）允许在 commit message 或 PR 描述中含验证结论替代

**lightweight 不降低验证标准，只放宽回执形式**：测试必须通过、行为变更
必须可验证、高风险判定标准不变。本节优先于下方"必需产物"中的回执要求
（冲突时以 governance marker 实际值为准）。


零额外依赖的收口门禁，按交付物形态执行：**代码变更**走两阶段（审查 → 验证闭环），**设计文档**走文档质量门禁。

## 代码变更形态

### 阶段一：最终 diff 审查

1. 固定本次任务目标、验收条件、基线和最终 diff；区分本次修改与用户已有改动。
2. 至少逐项检查：行为正确性与失败路径、项目宪章/规范、调用影响与兼容性、测试充分性、复杂度与维护性、文档/记忆一致性。
3. 命中安全触发条件时调用 `security-review`，并把其结果纳入同一门禁。
4. 每个发现给出准确文件/符号、可观察后果、触发条件、证据和最小修复方向；按 `CRITICAL/HIGH/MEDIUM/LOW` 标级。纯偏好不作为阻塞项。

#### 对抗式复核

对 HIGH/CRITICAL 和会阻止交付的结论，另做一次"证明它是误报"的复核：检查不可达分支、上游校验、事务边界、部署配置和已有测试。运行环境提供子 Agent **且当前上层指令允许委派**时，把 diff、验收条件与本轮发现交给一个**未参与实现的独立审查 Agent** 复核；不可用时在同一 Agent 中清空假设做第二遍，并在回执中披露这是同上下文复核。

只保留证据和置信度足够的发现，重复问题合并为根因项。任何审查维度未完成、工具异常或证据相互矛盾时 fail closed：结论只能更严，不得把缺失检查当作通过。

### 阶段二：验证闭环

先从项目宪章、根指令、CI 和构建文件提取真实门禁，不硬编码语言、覆盖率或工具。按项目与变更适用性运行，先快后慢：

1. 构建、编译或类型检查；
2. 格式化、lint 和静态分析；
3. 针对性测试、相关模块测试、必要的全量/集成/契约/并发/性能测试；
4. `security-review` 要求的扫描与安全回归；
5. spec/SDD、变更记录、用户文档和项目记忆的一致性检查。

命令失败或行为异常时进入 `systematic-debugging`；不得跳过、放宽断言或改写验收条件来制造绿色。因环境、权限或缺少依赖无法运行时，在回执中记录准确原因、影响和人工补验步骤。阶段一的修复必须重跑直接回归后重新过门，不能仅凭 diff 看起来合理就关闭。

## 设计文档形态（设计阶段质量门禁）

编码前的设计产出——②需求澄清结论、③《业务流程设计》、④《详细设计》、⑤任务清单——在进入下一阶段或人工确认前过同一门禁，检查四维：

1. **结构完整性**：对照骨架逐节核查（以项目内同类已认可文档的骨架为准）——概要设计（简介[业务目的/模块+角色范围/自包含术语]、总体设计[业务流+端到端闭环]、功能设计[UI 功能含界面+前端展示清单+原型引用；纯后端/SDK/CLI 免除 UI 部分，仅业务逻辑+专项]、依赖现有能力[一句话引用]、数据结构[表名级]、接口清单[功能级]）、详细设计（目标与边界/总体链路/领域模型/分侧设计/数据库/接口/验收要点/测试与验证设计）、实现计划（纵向可验证任务+每任务验证方式+引用编码规范）。**禁止项即缺口**：过程性标注语言（"用户拍板/已定/待确认"）、模块代号（M1/M2 式）、概要内出现类名、字段级表结构、消息链路、插件计数等实现细节（表名级汇总与接口清单除外——那是概要的应尽内容）、术语引用外部文档而不自包含。
2. **字段覆盖**：按统一产出字段的阶段标注核对——设计/契约/数据流、兼容性与风险、安全与威胁模型须在③④成型，测试接缝与用例在④⑤；缺失即逐项列出；尚缺事实或决策的内容处理规则分两层：**正式设计正文中不得存在未决项**——要么已确认、要么不写入；**独立的「待确认」登记区**（如②的问题清单、待核验标记）允许存在但必须显式标注确认方。**禁止的是**把待确认项混入正式正文当已定结论使用，或隐含未标注的不确定项冒充完成。
3. **一致性**：详细设计不推翻概要已确认结论（发现冲突即阻断并列出待裁决）；**验收要点必须能逐条溯源到②确认的需求场景与产出**——无场景依据的验收项即缺口；**澄清回溯**——④/评审中明确的口径（字段规则、边界行为、交互约定）须已按归属层回写上游（场景级→②、能力级→③），发现仅在下游记录而上游仍为旧口径或缺失的，即为割裂缺口；设计文档互相引用可达；与需求文档、业务域地图口径一致；跨文档引用的路径有效。
4. **可验证性**：验收条件可测量（能判 PASS/FAIL）；**测试与验证设计存在且完整**——接缝与分层明确（⑥ 有处落脚）、环境与数据可执行、可调试性（日志/错误码/诊断路径）有着落、留证方式明确；每个实现任务带验证方式；失败、边界与回退场景已覆盖。

**对抗式复核**：高风险设计决策（公共契约、数据模型、兼容性、安全）做一次"证明它错"的第二遍——与代码形态同规则（独立子 Agent 优先，否则清空假设并披露同上下文）。

结论与代码形态同一套枚举：`READY` / `NOT READY`（即需补充，逐项给出章节与缺口描述） / `NEEDS HUMAN REVIEW`。**回执频率**：②③ 的产出做快速审查，结论可并入④的定稿回执，不强制单独落盘；④ 设计定稿必须落独立回执，门禁执行表按上述四维逐项列检查与结果。轻量路线（短路/简版）无设计文档时不跑本形态。

## 验证回执（必需产物）

验证结论必须落持久回执，这是**声称验证通过的唯一证据形态**——对话内叙述的验证结果不构成完成依据。回执写入 `docs/delivery-receipts/YYYY-MM-DD-<中文任务名>.md`；**同日同任务重跑时追加 `-2`、`-3` 序号，不覆盖**（目录不存在则创建）：

```markdown
---
type: receipt
created: YYYY-MM-DD HH:MM
task: <一句话任务>
scope: <变更范围（文件/模块）>
verdict: READY / NOT READY / NEEDS HUMAN REVIEW
form: code / design
review: <审查结论；对抗复核为独立 Agent 或同上下文>
commit: <HEAD SHA 或 "uncommitted">
base: <基线 SHA 或 "none">
---

# 交付验证回执：<任务>

## 门禁执行

代码形态：检查=命令与退出码；设计文档形态：检查=四维（结构/字段/一致性/可验证性）逐项。

| 检查 | 方式/命令 | 结果 |
| --- | --- | --- |
| 构建 | <命令>（退出码 <code>） | <一句话> |
| 结构完整性 | 对照骨架逐节核查 | <结论/缺口> |
| 一致性 | 跨文档引用与上游结论比对 | <结论/缺口> |

未执行项必须写明原因与人工补验步骤，不得留空。

## 审查发现与处置

| 严重性 | 位置 | 证据 | 处置（已修复 / 留档 / 误报-复核依据） |
| --- | --- | --- | --- |

## 结论

<READY / NOT READY / NEEDS HUMAN REVIEW 及依据；人工审核项逐条列出>
```

只有适用门禁全部通过、没有未裁决的阻塞发现、代码与权威文档无已知冲突时才可 `READY`。项目要求人工审核时必须 `NEEDS HUMAN REVIEW`，即使自动检查全绿。回执落盘后不改写历史行；重跑门禁就写新回执。
