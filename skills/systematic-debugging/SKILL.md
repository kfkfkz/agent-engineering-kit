# Systematic Debugging

核心约束：**没有根因证据，不进入修复。** 诊断请求默认只报告原因；只有用户同时要求修复时才修改代码。

## 调用入口

- Claude Code：`/systematic-debugging [问题描述]`
- Codex：`$systematic-debugging [问题描述]`

## 统一诊断记录

在当前任务的既有 spec、变更记录或计划中维护以下字段，不另造平行文档：

`现象与期望 | 稳定复现/反证 | 根因链 | 影响范围 | 单一假设 | 最小修复 | 回归验证`

## 1. 建立事实

1. 完整读取错误、堆栈、日志和失败断言，记录准确位置与环境。
2. 用最小步骤稳定复现；不能复现时先收集数据，不猜原因。
3. 检查相关近期变更、依赖、配置和环境差异。
4. 多模块链路在每个关键接口观察输入、输出和状态，注意屏蔽敏感数据；异步问题等待业务条件，不用任意 sleep 猜时间。
5. 使用 `codebase-memory` 从症状沿 inbound 调用链或数据流向上追踪，直到找到错误值或状态的来源；图谱结论回到源码核实。

阶段产物必须回答：**在哪里坏、从哪里开始坏、为什么会坏。**

## 2. 比较模式

寻找同仓库可工作的相似路径，比较接口、调用顺序、配置、数据形态和依赖。列出能解释现象的差异，不凭“应该无关”提前排除。

## 3. 验证单一假设

明确写出：“根因是 X，因为证据 Y；如果成立，最小实验 Z 应产生结果 W。”一次只改变一个变量。实验不支持假设时撤回实验，带着新证据返回事实阶段，禁止叠加试错补丁。

## 4. 修复与回归

1. 调用 `tdd`，先在稳定的公共接缝建立能因预期原因失败的回归测试；无法自动化时说明原因并给出可重复验证脚本。
2. 只修复根因，不夹带无关重构；必要的防御校验放在能防止错误状态传播的实际层次，避免机械地层层重复。
3. 运行失败用例、相关测试和宪章要求的完整验证，确认不是只让断言变绿而问题仍存在。
4. 连续三个修复假设失败，或每次都暴露新的共享状态/散弹修改时，停止尝试并将其标记为架构问题；先形成架构候选和决策，再继续编码。

完成报告包含：已确认根因、证据链、修复范围、验证结果、残余风险；根因仍未知时明确写“未定位”，不得用推测冒充结论。
