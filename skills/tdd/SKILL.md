# Test-Driven Development

测试描述调用者可观察的行为，并通过项目的稳定公共接口验证。实现可以重构，行为不变时测试不应跟着移动。

## 调用入口

- Claude Code：`/tdd [行为或任务]`
- Codex：`$tdd [行为或任务]`

## 进入条件

1. 行为、验收条件和独立预期值已经明确；需求仍有实质歧义时先回到 spec。
2. Bug 已由 `systematic-debugging` 定位根因；红测试用于锁住复现，不替代诊断。
3. 从宪章和计划读取测试类型、覆盖率、性能及人工确认门槛。

## 选择测试接缝

接缝是调用者观察行为的稳定接口。已有、低风险接缝可由 Agent 直接选择并记录在计划/任务中；只有新增或改变公共契约、跨模块接口、数据 schema，或者多种接缝会导致不同架构时才请求人确认。

优先选择小接口承载较多行为的深模块。出现以下情况时不要为了测试继续制造抽象：

- 必须 mock 多个内部协作者或验证私有调用顺序；
- 需要抽出只被测试使用的浅函数，真实风险仍在编排处；
- 理解一个行为要跨越许多薄模块，修改同一规则要散落多处；
- 测试接口几乎与实现同样复杂。

把这些视为架构反馈。使用 `codebase-memory` 核验调用和变化热点，再做 deletion test：删除候选模块后，复杂度会集中到一个更小接口后面，还是只会扩散到调用方？只有前者才值得形成架构候选。架构调整先进入 `repo-delivery` 的设计/确认链，禁止在 RED 状态下顺手重构。

## 每个纵向切片

1. **RED**：只写一个行为测试；先运行并确认它因预期缺失行为而失败，而不是环境、编译或测试夹具错误。
2. **GREEN**：写满足当前测试所需的最少生产级代码，不预实现下一条行为，不用硬编码、放宽断言或跳过测试伪造通过。
3. **REFACTOR**：保持绿色，只做当前切片内的小型行为保持整理，如去重、命名和局部结构改善；公共接口或架构变化另走设计链。
4. 重复下一条行为。不要先批量写完所有测试再批量实现。

## 测试质量

- 名称表达业务行为而非方法调用；通过公共接口观察结果。
- 预期值来自 spec、已确认示例或固定事实，不用与实现相同的算法现场重算。
- 默认只在外部系统、时间、随机数、文件系统等真实系统接缝使用 mock；自有模块优先用真实实现，数据库优先用测试库。
- 异步测试等待可观察条件并设置有意义的超时；只有验证时间语义时才使用固定延迟并说明依据。
- 一个测试聚焦一个逻辑行为，但可包含证明该行为所需的相关断言。

## 收口

每个切片运行目标测试；阶段结束运行相关测试，交付前运行宪章要求的完整套件、覆盖率和静态检查。报告：已覆盖行为、采用的接缝、RED 证据、完整验证、未覆盖风险，以及是否发现需要另行决策的架构信号。
