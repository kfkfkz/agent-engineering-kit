把当前仓库变更从任务入口推进到可验证、可交接的完成状态。本技能只负责**提取门禁、路由和收口**：项目已有的 `AGENTS.md`、constitution、`.specify/`、SDD、版本文档和代码仍是权威来源，不复制全文，不新建一套平行文档体系。

## 调用入口

- Claude Code：`/repo-delivery [任务描述]`
- Codex：`$repo-delivery [任务描述]`
- 自然语言提出实现、修复、重构、迁移或完整交付请求时，也允许 Agent 根据 description 自动调用。

命令后的内容就是本次交付目标；未附参数时使用当前对话中最近的可执行任务。若上下文中没有可执行目标，只询问任务是什么，不自行臆造工作。

## 定位目标仓库

先解析本 `SKILL.md` 的真实路径（跟随符号链接），将技能目录向上三级作为目标仓库根目录；确认该目录包含 `.repo-memory-kit/manifest.json` 与 `docs/memory/RULES.md`。后续相对路径与命令以该仓库为准。校验失败时使用用户明确指定的仓库；仍无法唯一定位则询问，禁止在猜测目录执行。

## 0. 零阶段快速分流（先限预算，再深读）

在加载完整记忆、SDD、历史决策或做全图影响分析之前，先用低成本证据建立**临时 Route
Card**：只读用户请求、仓库根指令、governance marker、候选代码/测试入口和必要的目录清单。
根指令明确要求的前置文件照常读取，但不要因为“可能相关”遍历全部文档。然后运行
`.repo-memory-kit/bin/route-eval <仓库根> --card <临时卡片> --json`，按返回的
`execution_profile` 限制后续上下文、规划、设计、验证和回执详细度。

升级路线必须有**正向证据**：没有正向证据时不得升径；不能因为“尚未把整个仓库读完”、
Agent 主观谨慎或功能名称听起来重要而提高路线。能从仓库快速查明的问题不是
`intent_gaps=material`，未做调查也不能填写 `uncertainty=high`。以下字段按语义而非文件数猜测：

- `behavior_change=public` 只指外部 API/协议、持久化格式或向后兼容承诺；单个产品内部、
  局部可见的小功能仍是 `local`，不是因为“用户看得见”就算公共契约。
- `footprint.modules` 统计独立部署、独立版本或明确业务边界，不是源代码与测试目录的数量；
  同一实施单元内的 controller/service/test 和多文件修改仍计一个模块。
- `footprint.sessions` 统计已计划的跨会话交接/恢复，不是对话轮数或工具调用次数；当前会话
  内连续使用多个工具仍计一个 session。
- `planned_paths` 用于范围漂移检查；路径多本身不升级路线。

`route-eval` 返回 `route_fit=too_heavy` 时同样阻断。只有用户明确要求，或项目已有规则明确
要求更重路线，才可填写 `route_override.kind=user_requested|project_required` 和具体原因；
`project_required` 还必须用 `source` 指向根指令/constitution 的规则来源。项目底线能表达为
治理规则时优先使用 `min_route:<route>`，不得用空泛的“更稳妥”绕过。

执行预算必须落地：Direct 只做最小上下文、无独立计划/设计和定向验证；Bounded 只读目标
上下文、写紧凑计划/必要决策并做定向验证；Standard 才做影响级上下文和结构化计划；
Initiative 才加载项目级上下文并走完整 SDD。临时卡片在调查发现真实新证据后可更新，
但每次升径都要记录触发证据。

## 1. 提取宪章门禁

零阶段确定 `execution_profile` 后，通过仓库根部指令定位当前生效的 constitution/宪章；常见位置包括 `.specify/memory/constitution.md`，但不得仅凭路径猜测权威文件。只提取与本任务及所选路线相关的强制要求，形成一份短门禁清单，至少检查：

- 是否要求规范先于代码，以及哪个阶段必须人工确认；
- 当前设计正文是否必须保持单一有效口径，能否保留修订附录；
- 复用、复杂度记录、依赖引入和架构/模块边界；
- 数据分级、敏感信息投喂、安全编码及 AI 禁止参与的领域；
- 测试类型、失败场景和明确的覆盖率/性能门槛；
- 人工评审、文档语言、版本控制和同步提交要求。

具体技术栈、目录、层次、阈值和禁区以目标项目宪章的当前值为准，不把某个项目的 Java 版本或覆盖率推广为通用规则。**指令优先级**：用户本次明确要求 > 项目宪章/constitution > 根部指令（AGENTS/CLAU.md）> 本技能默认流程。更高优先级与更低级冲突时，按更高级执行并在首次进度更新中说明差异；仅当**同级**冲突无法调和时才请求裁决，不静默选边，也不因低级规则阻断用户已明确授权的工作。

## 2. 复杂度自适应路由

先做只读调查，再选择能够安全完成任务的最轻路线。**工作种类**（bug / feature /
refactor / migration）与**任务路线**正交：小型新增功能可以是 Bounded，跨服务复杂缺陷
可以是 Standard/Initiative，禁止仅凭“新功能/缺陷”标签决定流程。

| 任务路线 | 判定 | 最低交付链 |
| --- | --- | --- |
| Direct | 无行为变化、范围局部、低不确定性、容易回退 | 修改 → 针对性验证 |
| Bounded | 一个清晰目标、单模块/单仓库/单会话、局部行为变化、无高风险覆盖项 | 简短验收与范围 → 必要的 TDD → 定向测试 → 快速审查 |
| Standard | 跨模块、公共行为变化、实质意图缺口、难回退或命中风险覆盖项 | 影响分析 → 仅适用的设计 → 计划 → 实现 → 独立审查 |
| Initiative | 多仓库、较长多会话、多团队/并行工作流 | 完整 SDD → 可交付单元拆分 → 分批实现 → 集成门禁 |

风险覆盖项独立叠加：公共契约、schema/迁移、安全隐私、合规、不可逆操作、跨服务/
跨仓库、并发一致性和核心数据流。风险只增加相关强制步骤，不把无关 UI、API 或数据库
文档一并强加给任务。`strict/lightweight` 是**项目治理 profile**，只决定回执形态等
组织底线，不是任务复杂度；strict 下的安全 Bounded 任务仍然是 Bounded，只需正式回执。

### Route Card（计划契约）

在零阶段临时卡片上补充调查证据，形成短 Route Card。Direct 可只在首次进度中给出同等字段；其他路线写入当前任务
已有载体或临时文件，不为它新建一套提交进仓库的文档体系。用以下命令生成起点并校验：

```bash
.repo-memory-kit/bin/route-eval --init > /tmp/aek-route-card.json
# 填写 route、planned_paths、影响面与风险字段后校验
.repo-memory-kit/bin/route-eval <仓库根> --card /tmp/aek-route-card.json --json
```

Route Card 必须给出 `route/work_kind/intent_gaps/behavior_change`，预计路径与模块/仓库/
会话数，`reversibility/risk_overlays/coordination/uncertainty`、可选的 `route_override`，
以及专项检查和升级条件。校验输出的 `recommended_route` 是默认选择，`execution_profile`
是本任务允许的执行深度。
首次进度用一行报告：

`路线(所选/最低) | 意图缺口 | 影响面 | 可逆性 | 风险覆盖项 | 必需检查 | 升级条件`

`route-eval` 同时裁决安全性和经济性：路线过轻或无理由过重都会阻断。只有用户明确要求或
项目规则明确要求时，才允许用带具体原因的 `route_override` 选择高于 `recommended_route`
的路线。
治理规则可以用 `min_route:<route>`、`required_check:<name>`、
`review_depth:thorough` 叠加组织底线。
规划阶段由 Route Card 的风险覆盖项表达语义风险；路径和新增行规则在拿到最终 diff 后机械复核。

**动态升降径**：路线不是按任务名称一次定死。调查证明范围更小时可以降径；执行中发现
契约、数据模型、跨模块或其他超预期影响时必须更新 Route Card 并重新评估，从对应阶段
重入，而不是继续短路。已完成且仍合法的取证/测试可以复用，不做仪式性返工。

上游依据只存在于对话或个人脑中时，把它写入项目**已有**的权威载体；已有文档能表达时只引用和更新，不重复造文档。

以下属于默认高风险决策：外部 API/契约、数据库 schema 或数据迁移、安全与合规、核心数据流、跨服务/跨仓库边界、不可逆操作。高风险决策缺少明确依据时，在编码前请求人确认；项目宪章规定了更严格的确认门槛时从其规定。低风险实现细节可继续，除非不同选择会实质改变范围或结果。

## 3. 按需取上下文

1. 读取仓库根部指令和当前交付框架；constitution 已在门禁阶段读取，不重复加载。严格遵循
   `execution_profile.context_depth`：Direct/Bounded 不做全仓库上下文扩展。
2. 仅当任务相关且执行深度允许时读取 `docs/memory/PROFILE.md` 和 `docs/memory/README.md`；
   命中相关 pitfall/playbook/decision 才下钻全文。Direct 默认跳过全局画像，除非根指令强制。
3. 只读取与任务相关的规范、业务域地图、spec/SDD/变更记录；默认忽略 `old/`、归档和已废弃材料。
4. 结构化代码检索使用 `codebase-memory`：默认 Verify 级定位符号、调用链与影响范围；关键结论回到当前源码和测试核实。字符串、配置和未被索引的文件再用文本检索。
5. 动手前确认现有可复用能力、受影响契约、测试入口及相关记忆。涉及新依赖、外部集成、通用组件或关键技术选型时调用 `reuse-research`，给出采用/扩展/组合/自建及证据；已有路径明确的小改动不额外加流程。

## 4. 交付阶段与载体

阶段按任务路线启用，而不是按 bug/feature 标签启用：Direct 不产独立设计；Bounded 只在
项目现有载体中记录验收、范围、关键决策、风险与验证；Standard 只产出本次适用的设计；
Initiative 才默认执行 ①～⑥ 完整链。高风险决策强制停下等裁决，实现细节可并行起草。
**Standard 需要正式设计阶段或 Initiative 的 ③④⑤ 文档经 `design-pipeline` 产出与把关：
每阶段过 doc-gate 硬校验 + AI 评审 + 确定性门禁，PASS 即冻结（哈希落
reviews/<阶段>.gate.json）。**

**① 需求拆分**：基于当前代码把需求拆成可独立交付的功能点清单（登记进 docs/01-需求/ 索引，原始材料归 01-需求/NNN-名称/）。用 `codebase-memory` 定位现有能力、调用链与影响面，业务域地图与 `memory-recall` 检索既有知识（域条目、坑、决定）；产出功能点清单 + 待澄清问题清单。清单最小格式：`功能点 | 类型(新增/修改/复用) | 所在模块/菜单(粗位) | 依赖 | 风险`——①只定**范围与归属**（哪些做、归谁、依赖谁），不做设计（界面/交互/落位归③）；①和③越界时以"①不出现界面描述、③不重新拆分"为准。

**② 需求确认**：原始需求常常只有几句话——先依据当前实际业务把它衍生为**具体需求场景**，每个场景定义**可观察的产出**（用户在哪个页面看到什么、系统对外呈现什么结果）；验收依据优先级：本次用户明确要求 > 已确认的正式规范/合同/Spec > 针对缺口补充并确认的派生场景。**三者冲突时高级别覆盖低级别，并在④中说明差异**。边界、优先级、兼容性、数据口径等需人裁决的问题集中列出交用户。范围内可继续起草，范围级分歧必须停下等确认——AI 草稿不代替需求决策。

**③ 概要设计**：基于②确认的场景与产出，回答"要新增/修改哪些功能点、落在哪个页面、怎么交互"。**先定位项目内同类已认可文档并对齐其骨架**（有先例沿用先例，不按通用模板另起炉灶）；无先例时用默认六节骨架，每节有"必须/禁止"：

1. **简介**：目的写**业务目的**（推广什么能力、达成什么业务效果、对存量的影响）——禁止写成文档自身的方法说明；范围写**涉及模块 + 各模块参与角色**（角色→参与的流程节）——禁止指向需求文档的范围清单；术语在本文档内**自包含定义**——禁止"沿用需求§X"式引用。
2. **总体设计**：一张业务流（模块关系与业务流向，可按配置/执行/治理/观测等域切分）+ 端到端业务闭环；不设模块边界表（与范围重复，至多一句边界总原则）。
3. **功能设计**（按能力逐节，三件套）：**界面**（菜单位置一句话 + 原型图；落位方案细节归④；仅面向 UI 的功能需要，纯后端/SDK/CLI/算法库不适用）；**前端展示清单**（表单字段/表格列/操作/统计条逐项列——它是④接口设计的验收依据，必须完整；同样仅 UI 功能需要）；**业务逻辑**（编号流程与规则——所有功能必含）。本功能特有的专项主题（如事件生成、服务资源保护、性能保障）作为必备节。
4. **依赖的现有能力**：**一句话引用**（"X/Y 为既有能力，直接复用，清单与接线见详细设计"）——禁止在此展开类名、消息链路、插件计数等实现细节（表名级汇总只出现在第 5 节）。
5. **数据结构**：表名级汇总表（修改/平台新增/审计/复用/SDK 本地），字段级指向④。
6. **接口设计**：清单表（功能/接口/类型），字段级指向④。

**界面描述必须有真实依据**（仅面向 UI 的功能）：菜单树从运行环境接口实时拉取（不用记忆），页面文案取自前端源码/i18n/编译包字符串，设计令牌取自前端源码 CSS 变量——禁止凭空造 UI。**面向 UI 的功能原型是标准交付物**：有产品设计类技能时优先产出可评审原型（如 `00-交互原型.html`），并用无头浏览器渲染 PNG 嵌入文档（如 `google-chrome --headless --screenshot=p.png --window-size=1920,N file://…`），新增元素标注「新增」。**写作纪律**：不出现"用户拍板/已定/待确认 X1"等过程性标注——决策溯源在需求文档的决策记录，概要只呈现结果；模块不用代号，直接中文名。新依赖/外部集成走 `reuse-research` 证据化决策。

载体（单一落位，不双头）：**功能级设计集统一落 `docs/03-SDD/NNN-名称/`**（与 `docs/01-需求/NNN-名称/` 原始需求同号同名）——需求分析.md + 概要设计.md +（界面触达时）UI设计.md + 详细设计.md + API设计.md + 数据库设计.md + 任务清单.md + 测试方案.md + 线上联调功能验证清单.md + 终稿.md；架构级概要仅在跨域架构变更或技术选型时补 `03-架构设计/`。改变公共契约、跨服务边界或数据模型的决策点交人确认。

**④ 详细设计**：以③的功能点与原型定位改动位置——每个接口、表结构、流程改动都能指到具体页面与功能点。产出《功能名-详细设计》——骨架：目标与边界（功能定位/范围与边界）→ 总体链路与口径 → 领域模型 → 分侧设计（按系统实际切分，如平台侧/SDK 侧/各服务侧）→ 数据库详细设计 → 接口详细设计 → 验收要点（**逐条溯源到②的场景与产出**）→ **测试与验证设计**：

- **测试接缝与分层**：单元/集成/契约/端到端各在哪层、落在哪些稳定接缝（⑥ 的 tdd 在这些接缝上执行，不另选）；涉及界面/流程/环境不可自动化时给出替代验证方式；
- **测试环境与数据**：用哪个环境、可复用的既有测试数据、造数与清理方案；
- **可调试性**：关键链路的日志点、错误码、指标与诊断入口（失败时按什么路径定位）；
- **验证执行与留证**：适用的项目门禁、回归范围（哪些存量必须不动）、测试报告与回执的落点、覆盖率或性能口径。

不推翻已确认的概要结论；缺失维度以待核验标记补齐，不虚构业务事实。

**澄清回溯（防口径割裂）**：设计或评审中明确的事项按其归属层回写上游——场景边界、可观察产出变化回②；能力划分、交互约定、前端展示清单变化回③；纯技术实现细节留④不向上推。**仅在下游记录而上游未同步＝口径割裂，视为该层未完成**；回写上游后本轮设计依据同步引用新口径。

载体按上述统一口径执行。项目另有既定设计模板（如 lld 四件套）时从项目惯例。

**⑤ 任务拆分**：详细设计拆成纵向可验证的任务清单（03-SDD 的 任务清单.md，或项目既有 Spec Kit tasks），每任务带验证方式——任务级验证方式是④测试与验证设计在该任务上的具体化，不是另行发明。

**⑥ 编码与验证**：`tdd` 纵向切片实现 → `delivery-gate` 门禁与验证回执（形态由 `.repo-memory-kit/governance` 标记决定：strict=独立文件，lightweight=低风险允许 commit message 内嵌）→ 回写设计文档与业务域地图 → `memory-capture` 候选。

**确认矩阵**（谁在什么节点签什么——灰色情况对照此表判定，不确定走重）：

| 节点 | 产出 | 确认方 |
| --- | --- | --- |
| ② 场景与产出 | 需求分析（场景清单 + 可观察产出） | 用户（缺它验收无依据；签写冻结记录 + doc-gate freeze） |
| ③ 概要 → ④ 过渡 | 概要文档 | `design-pipeline` 门禁（doc-gate PASS = 冻结）；高风险决策（公共契约/数据模型/兼容）人裁决 |
| UI设计（触 UI 时） | UI设计.md | `design-pipeline` 门禁 + AI 视觉评审 |
| ④ 设计定稿 | 详细设计（含测试与验证设计） | `design-pipeline` 门禁（gate.json 落盘）；宪章要求的人审项逐条列出 |
| ⑤ 任务清单 + 测试方案 | 实现计划 + 用例 | `design-pipeline` 计划阶段门禁（追踪链 A→TC→T 全机械校验） |
| ⑥ 完成 | 代码 + 验证回执 | `delivery-gate` 代码门禁 + route-eval 路线/漂移裁决 + governance-eval 治理裁决 + 回执；宪章人审项照旧 |
| Direct / Bounded | 短路或简版产物 | 针对性验证 / 根因链+回归；回执形态由治理 profile 决定；发现超预期影响面 → 重新评估路线 |

载体选择：存在 `.specify/` 沿用其 spec/plan/tasks；已有 SDD、版本文档或变更记录体系在对应版本和业务域下更新现有链路；两者都没有时按项目惯例维护简短计划，不为单次任务搭建新流程目录。Bounded 至少明确：验收条件、范围与不做事项、关键决策、风险、验证方式、需同步的权威文档，以及本次适用的宪章门禁如何满足。可从仓库直接查明的问题先查，不把它们留作用户待办。

无论项目使用哪种文件名或模板，交付信息都必须能映射到同一组语义字段（括号为产出阶段）：

`目标与范围(①②) | 当前证据/根因与复用依据(①) | 行为与验收(②④) | 设计/契约/数据流(③④) | 兼容性与风险(③④) | 安全与威胁模型(③④) | 测试接缝与用例(④⑤) | 实施任务(⑤) | 验证结果(⑥) | 文档与记忆影响(⑥)`

项目已有模板时把字段填入对应章节，不为了统一外观破坏项目的事实源；缺少关键字段时补进原文档的合适章节，不创建“补充说明”文件。

## 5. 实现与验证

按可验证的小批次实现，遵守已提取的复用、依赖、模块边界和安全门禁，避免夹带无关重构。可观察行为默认 `tdd` 按纵向切片实现。**TDD 不适用条件**（满足其一即可替代验证，需记录理由）：配置文件、纯文档、生成物、无调用方的脚本、只改数据不改逻辑的迁移。不满足任何不适用条件的可观察行为变更，必须走 `tdd`。认证授权、外部输入、数据库/文件/网络/命令、密钥、支付回调、依赖或 Agent 配置变更调用 `security-review`。测试首先满足宪章的明确要求，再按风险补直接相关的单元、集成、契约、性能、构建或静态检查。任何失败进入 `systematic-debugging`，不用放宽断言、跳过检查或改写目标来制造通过。

在关键阶段用一行简报保持上下文：

`路线(所选/最低) | 宪章门禁 | 已用依据 | 风险覆盖项 | 验证状态 | 下一步`

只在存在真实分歧、外部权限或高风险未决事项时暂停等待；AI 草稿不得自行标记为“已确认”。

## 6. 收口

1. 固定基线，运行 `.repo-memory-kit/bin/route-eval <仓库根> --card <Route Card> --git-ref <基线>`（同时纳入 tracked 与 untracked）；CI 已提供可信完整 diff 时可用 `--diff <文件>`。路线过轻或出现未计划路径时先说明新增范围、更新计划/升径，禁止把漂移直接写成“已知偏差”后放行。随后调用 `delivery-gate` 做证据化审查、治理裁决、验证闭环并落**验证回执**。
2. 门禁发现修复并补直接回归后重过 `delivery-gate`；**修复落点是受该口径影响的全部层级文档，不只改被审的那份**（场景级回②、能力级回③——见④「澄清回溯」）；验证结论以持久回执为唯一证据（载体由 `.repo-memory-kit/governance` 决定），没有回执不得声称验证通过。
3. 将实际实现直接整合回项目既有 spec/SDD/变更记录的对应章节，清除失效口径；除非项目明确要求，禁止靠“补充说明”叠加互相矛盾的新旧设计。代码与文档矛盾时必须显式指出，不擅自替人确认业务决定。
4. 检查本次变更影响了哪些已有记忆；需要时调用 `memory-check`。回写了业务域地图条目时，运行 `.repo-memory-kit/bin/domain-check` 核验索引登记与证据路径。
5. 功能验收或缺陷修复完成后，调用 `memory-capture` 提取候选。候选须先展示给用户确认，确认后才能写入并运行 `memory-build`。
6. 汇报完成内容、宪章符合性、验证证据（引用回执）、所需人工评审、未决风险和建议提交范围；没有实际执行就不得声称已提交或推送。任务中断或跨 Agent/会话转交时调用 `task-handoff`，把可恢复状态写入已有任务载体。

完成标准：适用宪章门禁和验收条件已验证且验证回执已落盘；没有未裁决的权威冲突或被隐藏的高风险事项；代码与权威文档无已知冲突；记忆影响已处理或候选已提出。宪章要求人工审核时，“AI 实现完成”不等于“可进入生产”。
