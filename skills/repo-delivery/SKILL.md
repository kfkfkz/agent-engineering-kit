把当前仓库变更从任务入口推进到可验证、可交接的完成状态。本技能只负责**提取门禁、路由和收口**：项目已有的 `AGENTS.md`、constitution、`.specify/`、SDD、版本文档和代码仍是权威来源，不复制全文，不新建一套平行文档体系。

## 调用入口

- Claude Code：`/repo-delivery [任务描述]`
- Codex：`$repo-delivery [任务描述]`
- 自然语言提出实现、修复、重构、迁移或完整交付请求时，也允许 Agent 根据 description 自动调用。

命令后的内容就是本次交付目标；未附参数时使用当前对话中最近的可执行任务。若上下文中没有可执行目标，只询问任务是什么，不自行臆造工作。

## 定位目标仓库

先解析本 `SKILL.md` 的真实路径（跟随符号链接），将技能目录向上三级作为目标仓库根目录；确认该目录包含 `.repo-memory-kit/manifest` 与 `docs/memory/RULES.md`。后续相对路径与命令以该仓库为准。校验失败时使用用户明确指定的仓库；仍无法唯一定位则询问，禁止在猜测目录执行。

## 1. 提取宪章门禁

先通过仓库根部指令定位当前生效的 constitution/宪章；常见位置包括 `.specify/memory/constitution.md`，但不得仅凭路径猜测权威文件。只提取与本任务相关的强制要求，形成一份短门禁清单，至少检查：

- 是否要求规范先于代码，以及哪个阶段必须人工确认；
- 当前设计正文是否必须保持单一有效口径，能否保留修订附录；
- 复用、复杂度记录、依赖引入和架构/模块边界；
- 数据分级、敏感信息投喂、安全编码及 AI 禁止参与的领域；
- 测试类型、失败场景和明确的覆盖率/性能门槛；
- 人工评审、文档语言、版本控制和同步提交要求。

具体技术栈、目录、层次、阈值和禁区以目标项目宪章的当前值为准，不把某个项目的 Java 版本或覆盖率推广为通用规则。宪章比本技能默认流程更严格时执行宪章；宪章、根部指令、当前 spec 或用户目标相互冲突时，列出冲突及影响并请求裁决，不静默选边。

## 2. 入链判定

在宪章门禁内选择最轻且足够的路线，并在首次进度更新中说明：

| 路线 | 判定 | 交付链 |
| --- | --- | --- |
| 直接修改 | 文案、格式或明显不改变行为的小改动 | 修改 → 针对性验证 |
| 缺陷修复 | 当前实现偏离已确认行为 | `systematic-debugging` 根因链 → `tdd` 回归测试 → 最小修复 → 回归验证 |
| 既有变更 | 修改现有行为、契约或技术基线 | 影响面拆分（① 简版）→ 详细设计 → 实现计划 → 实现 → 文档回写 |
| 新功能 | 引入新行为、能力或关键设计决定 | ① 需求拆分 → ② 需求确认 → ③ 概要设计 → ④ 详细设计 → ⑤ 任务拆分 → ⑥ 编码与验证 |

影响跨模块、改公共契约或动数据模型的既有变更，按新功能链走。

上游依据只存在于对话或个人脑中时，把它写入项目**已有**的权威载体；已有文档能表达时只引用和更新，不重复造文档。

以下属于默认高风险决策：外部 API/契约、数据库 schema 或数据迁移、安全与合规、核心数据流、跨服务/跨仓库边界、不可逆操作。高风险决策缺少明确依据时，在编码前请求人确认；项目宪章规定了更严格的确认门槛时从其规定。低风险实现细节可继续，除非不同选择会实质改变范围或结果。

## 3. 按需取上下文

1. 读取仓库根部指令和当前交付框架；constitution 已在门禁阶段读取，不重复加载。
2. 若存在 `docs/memory/PROFILE.md`，先读画像，再查 `docs/memory/README.md`；命中相关 pitfall/playbook/decision 才下钻全文。
3. 只读取与任务相关的规范、业务域地图、spec/SDD/变更记录；默认忽略 `old/`、归档和已废弃材料。
4. 结构化代码检索使用 `codebase-memory`：默认 Verify 级定位符号、调用链与影响范围；关键结论回到当前源码和测试核实。字符串、配置和未被索引的文件再用文本检索。
5. 动手前确认现有可复用能力、受影响契约、测试入口及相关记忆。涉及新依赖、外部集成、通用组件或关键技术选型时调用 `reuse-research`，给出采用/扩展/组合/自建及证据；已有路径明确的小改动不额外加流程。

## 4. 交付阶段与载体

阶段按路线分级启用：直接修改与缺陷修复走短路，既有变更从影响面进入，只有新功能走全链。上游阶段未确认不进入下一阶段定稿——高风险决策强制停下等裁决，实现细节可并行起草。**设计产出在进入下一阶段或人工确认前，经 `delivery-gate` 的文档形态做质量审查（结构/字段/一致性/可验证性，见该技能「设计文档形态」节）；设计定稿（④ 完成）必须过检并落回执，才能进入任务拆分与编码。**

**① 需求拆分**：基于当前代码把需求拆成可独立交付的功能点清单。用 `codebase-memory` 定位现有能力、调用链与影响面，业务域地图与 `memory-recall` 检索既有知识（域条目、坑、决定）；每点标注依赖关系、受影响契约与风险，产出功能点清单 + 待澄清问题清单。

**② 需求确认**：边界、优先级、兼容性、数据口径等需人裁决的问题集中列出交用户。范围内可继续起草，范围级分歧必须停下等确认——AI 草稿不代替需求决策。

**③ 概要设计**：产出《功能名-业务流程设计》——骨架：简介（目的/范围/术语说明）→ 需求描述 → 总体设计（架构描述/业务闭环）→ 功能设计（按能力逐节：依赖的现有能力、各能力的流程与规则）→ 数据结构 → 接口设计。粗粒度：讲清业务闭环与能力划分，细节指向详细设计文档；新依赖/外部集成走 `reuse-research` 证据化决策。技术选型与改变公共契约、跨服务边界或数据模型的决策点交人确认。

**④ 详细设计**：产出《功能名-详细设计》——骨架：目标与边界（功能定位/范围与边界）→ 总体链路与口径 → 领域模型 → 分侧设计（按系统实际切分，如平台侧/SDK 侧/各服务侧）→ 数据库详细设计 → 接口详细设计 → 验收要点。以③为上游展开，不推翻已确认的概要结论；缺失维度以待核验标记补齐，不虚构业务事实。

③④ 两份文档都落架构设计载体：SDD 项目放 `03-架构设计/NN-功能名-业务流程设计.md` 与 `NN-功能名-详细设计.md`，扁平 docs 项目按项目惯例（如 `YYYY-MM-DD-功能名-*.md`）；头部标注文档版本，两文互相引用（概要指向详细看细节，详细引用概要看闭环）。项目另有既定设计模板（如 lld 四件套）时从项目惯例。

**⑤ 任务拆分**：详细设计拆成纵向可验证的任务清单（SDD `06-实现计划/` 或 Spec Kit tasks），每任务带验证方式与引用的编码规范。

**⑥ 编码与验证**：`tdd` 纵向切片实现 → `delivery-gate` 门禁与验证回执 → 回写设计文档与业务域地图 → `memory-capture` 候选。

载体选择：存在 `.specify/` 沿用其 spec/plan/tasks；已有 SDD、版本文档或变更记录体系在对应版本和业务域下更新现有链路；两者都没有时按项目惯例维护简短计划，不为单次任务搭建新流程目录。轻量路线（短路/简版）至少明确：验收条件、范围与不做事项、关键决策、风险、验证方式、需同步的权威文档，以及本次适用的宪章门禁如何满足。可从仓库直接查明的问题先查，不把它们留作用户待办。

无论项目使用哪种文件名或模板，交付信息都必须能映射到同一组语义字段（括号为产出阶段）：

`目标与范围(①②) | 当前证据/根因与复用依据(①) | 行为与验收(②④) | 设计/契约/数据流(③④) | 兼容性与风险(③④) | 安全与威胁模型(③④) | 测试接缝与用例(④⑤) | 实施任务(⑤) | 验证结果(⑥) | 文档与记忆影响(⑥)`

项目已有模板时把字段填入对应章节，不为了统一外观破坏项目的事实源；缺少关键字段时补进原文档的合适章节，不创建“补充说明”文件。

## 5. 实现与验证

按可验证的小批次实现，遵守已提取的复用、依赖、模块边界和安全门禁，避免夹带无关重构。可观察行为默认调用 `tdd` 按纵向切片实现；配置、纯文档、生成物或无法自动化的变更可使用替代验证，但必须记录原因。认证授权、外部输入、数据库/文件/网络/命令、密钥、支付回调、依赖或 Agent 配置变更调用 `security-review`。测试首先满足宪章的明确要求，再按风险补直接相关的单元、集成、契约、性能、构建或静态检查。任何失败进入 `systematic-debugging`，不用放宽断言、跳过检查或改写目标来制造通过。

在关键阶段用一行简报保持上下文：

`路线 | 宪章门禁 | 已用依据 | 待决策 | 验证状态 | 下一步`

只在存在真实分歧、外部权限或高风险未决事项时暂停等待；AI 草稿不得自行标记为“已确认”。

## 6. 收口

1. 调用 `delivery-gate` 执行收口门禁：阶段一对最终 diff 做证据化审查（对照验收条件、统一交付字段和宪章门禁，区分本次修改与用户已有改动；高危或阻塞发现做对抗式复核）；阶段二按项目适用门禁执行验证闭环并落**验证回执**。外部 review CLI 只在用户另行安装并明确要求时使用。
2. 门禁发现修复并补直接回归后重过 `delivery-gate`；验证结论以 `docs/delivery-receipts/` 中的回执为唯一证据，没有回执不得声称验证通过。
3. 将实际实现直接整合回项目既有 spec/SDD/变更记录的对应章节，清除失效口径；除非项目明确要求，禁止靠“补充说明”叠加互相矛盾的新旧设计。代码与文档矛盾时必须显式指出，不擅自替人确认业务决定。
4. 检查本次变更影响了哪些已有记忆；需要时调用 `memory-check`。
5. 功能验收或缺陷修复完成后，调用 `memory-capture` 提取候选。候选须先展示给用户确认，确认后才能写入并运行 `memory-build`。
6. 汇报完成内容、宪章符合性、验证证据（引用回执）、所需人工评审、未决风险和建议提交范围；没有实际执行就不得声称已提交或推送。任务中断或跨 Agent/会话转交时调用 `task-handoff`，把可恢复状态写入已有任务载体。

完成标准：适用宪章门禁和验收条件已验证且验证回执已落盘；没有未裁决的权威冲突或被隐藏的高风险事项；代码与权威文档无已知冲突；记忆影响已处理或候选已提出。宪章要求人工审核时，“AI 实现完成”不等于“可进入生产”。
