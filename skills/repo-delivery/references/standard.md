# Standard 路线

本文件是 `repo-delivery.route.standard` 的唯一权威，同时是 Initiative 的共用设计与实现规则。

## 门禁与上下文

1. 从生效的 constitution/根指令只提取本任务强制项：spec 先行、模块边界、数据安全、测试/性能、
   人工评审、文档与版本控制。优先级为用户本次要求 > constitution > 根指令 > 技能默认。
2. 使用 `codebase-memory` 做 Verify 级结构检索、调用链和影响分析，关键结论回到源码/测试；字符串和
   未索引脚本再文本检索。只展开相关记忆、规范和 SDD，不遍历归档。Memory 通过内部
   `memory-recall --context-json` 绑定当前 Route/subject/session，Standard 默认候选≤8、正文≤3；
   只消费机器选择的 `expanded`，风险候选截断时携目的扩展或升径，不把 top-k 当完整证明。
3. 新依赖/关键选型先 `reuse-research`；安全敏感变更走 `security-review`。

## 适用设计

Standard 采用“影响分析 → 仅适用的设计 → 计划 → 实现 → 独立审查”。正式设计使用
`design-pipeline`，每阶段经结构校验、独立评审与确定性门禁；公共契约、数据模型、跨服务或不可逆
决策缺依据时交人确认。

- 需求只写场景、可观察产出、边界和验收，不在需求阶段提前写界面/实现。
- 概要说明能力、业务闭环、复用、表/接口清单；面向 UI 才需要基于真实菜单、文案、令牌的原型。
- 详细设计把功能点落到接口、状态、数据与失败语义，并定义单元/集成/契约/E2E 接缝、环境数据、
  日志诊断和验证证据。
- 任务必须是可独立验证的纵向切片，包含设计/测试引用、预计路径和可执行验证；不要按层横切。

下游发现口径变化时按归属回写：场景/产出回需求，能力/交互回概要，纯实现留详细设计；不得用
“补充说明”叠加相互矛盾的新旧口径。

## 实现与审查

- 按 `tdd` 做 RED→GREEN→REFACTOR；难测、过度 mock 或散弹修改视为架构反馈，不在 RED 时顺手重构。
- 持续更新任务执行记录，但不反复冻结计划；出现契约、数据模型或范围新证据时重新路由。
- AI 评审是 sensor，确定性工具/策略才产生 gate verdict。失败进入 `systematic-debugging`，不放宽断言。
- 完成实现后完整读取 `evidence-closeout.md`。
