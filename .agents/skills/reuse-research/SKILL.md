# 复用优先调研

目标是用足够证据回答“已有能力能否直接采用、扩展或组合”，而不是为了搜索而搜索。

## 触发与边界

新依赖、外部服务、通用工具、框架能力、协议实现或跨项目组件必须先执行。已有仓库能力明确、纯文案、机械修改和局部修复无需额外调研。用户只要求评估时不安装依赖、不修改外部系统。

## 流程

1. 从项目代码、依赖清单、内部包、项目记忆与权威设计中先找现有能力；结构检索优先使用 `codebase-memory`。
2. 仍有空缺时，按任务可用渠道查询官方文档、包仓库、MCP/插件目录及 GitHub。技术结论优先官方或一手来源，并记录版本与查询日期。
3. 对候选比较：能力匹配、集成成本、维护活跃度、许可证、供应链与安全风险、运行时/团队负担、退出成本。
4. 明确选择一种结论：
   - `采用`：现成能力满足需求；
   - `扩展`：已有能力只缺小范围适配；
   - `组合`：多个稳定能力能闭合需求；
   - `自建`：候选不满足约束，并给出反证。
5. 把结论写入项目既有 spec/plan/decision 载体，不另建平行报告。

## 输出契约

```text
需求与约束：
已查渠道与证据：
候选比较：
决策：采用 / 扩展 / 组合 / 自建
未选原因：
依赖、许可与安全影响：
需要人工确认的事项：
```

不得把“没搜到”写成“不存在”；搜索受限或结果不完整时披露范围和置信度。引入依赖仍须遵守项目宪章与人工审批门槛。
