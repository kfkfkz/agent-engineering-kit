对当前仓库 `docs/memory/` 全部条目执行巡检（压缩与矫正），规则见 `docs/memory/README.md` 的「条目大小与时效」一节。

**前置依赖（默认强制）**：需要结构化代码检索工具（代码知识图谱类，如 codebase-memory MCP；或提供符号定位、调用关系、索引覆盖信号的等效 codegraph 工具）。grep 有三个结构性盲区，不能作为巡验兜底：路由前缀配置在 context-path（字面量搜不到）、类/方法改名后关键字静默失效、无索引覆盖信号无法判断结果可信度。工具不可用时报告缺失并终止，除非用户明确要求降级（降级报告必须标注"grep 降级，置信度低"）。

## 执行步骤

1. **前置检查**：确认结构化检索工具可用、当前项目已索引且索引未陈旧（索引缺失或陈旧先重建再巡检）。
2. **提取校验点**：逐条读取 `docs/memory/pitfalls/` 与 `docs/memory/playbooks/` 下的条目。没有「校验点」小节的，从正文提取可机器核验的事实（接口路由、类/方法名、文件路径、配置键）生成该小节。
3. **代码级核验**：对每个校验点比对当前代码库（符号定位用图工具；grep 仅用于字面量、配置文件与非代码文件）：
   - 接口路由：在 Controller / 网关配置中确认前缀与路径仍存在；
   - 类/方法：确认仍存在且关键逻辑未变（如查询条件、状态枚举值）；
   - 文件路径：确认文件仍存在；
   - 环境相关 ID（资源 ID、策略 ID 等）：无法从代码核验的标注"需环境实测确认"。
3. **矫正**：失配的条目修正正文与校验点，更新「最后有效」日期；无法确认新旧状态的，不改状态，列入待人工确认清单。
4. **压缩**：pitfall 超过 60 行、playbook 超过 150 行的条目——保留「状态/触发/根因结论」，把过程细节（报文、步骤明细）下沉到对应权威文档并保留指针。
5. **索引同步**：更新 `docs/memory/README.md` 索引表的一句话描述与状态，以及「最近巡检」记录。
6. **输出报告**：列出本次矫正了什么、压缩了什么、哪些条目存疑待人工确认。

## 边界

- 巡检只修改 `docs/memory/` 内的文档，**不改任何代码**。
- 状态改为 `deprecated` 必须人工确认，巡检只能提出建议。
- 发现条目背后的代码缺陷有了新变化时，只更新条目，不顺手修代码——修代码走正常 bug 修改流程。
